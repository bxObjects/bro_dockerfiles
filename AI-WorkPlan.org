* Stage 3: Add rootless-sysd (Podman) variant

Goal: Add a third peer to the confined/privileged init-profile axis: a
rootless Podman systemd container that delivers the =privileged= payoff
(systemd as PID 1) with the =confined= security posture (unprivileged,
userspace). Motivated by the multi-tenant "N engineers on one shared VM"
use case, where Docker =--privileged= is a security dealbreaker but engineers
still need systemd fidelity inside their dev box.

Note on the model: the directory level formerly read as "privilege level"
(confined vs privileged) is now better understood as an "init/isolation
profile" axis. The three peers are named by property, not by tool:
=confined= (docker, unprivileged, no systemd), =privileged= (docker,
--privileged, systemd), =rootless-sysd= (podman, unprivileged, systemd).

* Stage 4: Host cgroup constraints and the cgroup-v1 privileged overlay

Goal: Capture which of the four models actually work on a given host as a
function of its cgroup version and privilege policy, and provide a working
systemd option for old (cgroup v1) hosts that cannot be rebooted. Driven by a
concrete situation: a corporate AWS *RHEL 8.10* host, still on cgroup v1, that
cannot be rebooted.

** Background: cgroup v1 vs v2 decision matrix

The init/isolation profiles depend on the HOST cgroup version. You cannot
switch v1 <-> v2 at runtime --- the unified hierarchy is chosen at boot.
Check with: =stat -fc %T /sys/fs/cgroup= (=cgroup2fs= = v2; =tmpfs= = v1/hybrid).

| Model                     | cgroup v1 host                         | cgroup v2 host |
|---------------------------+----------------------------------------+----------------|
| confined (docker/podman)  | works (cgroup-agnostic)                | works          |
| privileged sysd (docker)  | works, but needs the v1 compose overlay| works (v2 yml) |
| rootless-sysd (podman)    | DOES NOT WORK (no v1 rootless deleg.)  | works          |
| Vagrant VM                | works IF /dev/kvm present              | same           |

Key facts established:
- *rootless-sysd requires cgroup v2.* cgroup v1 has no safe delegation model,
  so an unprivileged user cannot get a writable cgroup subtree; rootless
  systemd-as-PID-1 and rootless cpu/mem limits simply do not work on v1.
  RHEL 8 hybrid mounts a v2 node at =/sys/fs/cgroup/unified= but it carries no
  controllers, so this does not rescue rootless delegation.
- *privileged sysd works on v1* via the classic recipe: =--privileged=, mount
  =/sys/fs/cgroup:ro= + =/sys/fs/cgroup/systemd:rw=, tmpfs on =/run /run/lock=,
  and NO =cgroup: host= (cgroup namespaces are a newer-kernel feature).
- *Vagrant on AWS* needs nested virtualization (=/dev/kvm=), available only on
  =.metal= instance types --- orthogonal to the cgroup question.

** RHEL 8.10 specifics (the work host)

- RHEL 8 (kernel 4.18) *supports* cgroup v2 but *defaults to v1/hybrid*.
- The supported flip is a boot-time kernel arg + reboot:
  =sudo grubby --update-kernel=ALL --args="systemd.unified_cgroup_hierarchy=1"=
  then reboot; then add a user delegation drop-in
  (=/etc/systemd/system/user@.service.d/delegate.conf= with
  =Delegate=cpu cpuset io memory pids=).
- *Constraint: the host cannot be rebooted.* Therefore it stays on cgroup v1
  and *rootless-sysd is unavailable there*. No runtime/userspace workaround
  exists.
- No-reboot options on that host: =confined= always; =privileged= sysd via the
  v1 overlay *iff* =--privileged= is permitted.
- AWS-native escape hatch that avoids rebooting the pet: stand up a *new*
  instance already on cgroup v2 (RHEL 9 / Amazon Linux 2023 default to v2, or a
  RHEL 8 launch template with the kernel arg baked into user-data), and a
  =.metal= type if the Vagrant/true-VM path is also wanted.

** Determining whether =--privileged= is allowed

"I have root" answers a different question than "am I authorized." Two levels:
- *Technical (can the daemon do it):* check for an authorization plugin
  (=docker info --format '{{.Plugins.Authorization}}'=), userns-remap/rootless
  mode (=docker info | grep -iE 'userns|rootless'=), then empirically test ---
  =docker run --rm --privileged busybox sh -c 'mount -t tmpfs none /mnt && echo PRIV_OK'=.
  =PRIV_OK= = permitted; "authorization denied by plugin" = forbidden.
- *Policy (are you sanctioned):* look for a runtime-security agent
  (falco/twistlock/prisma/aqua/sysdig/crowdstrike) that may allow-but-flag
  privileged containers, and confirm with the security/platform team. On an
  audited corporate host, "root can" != "security permits".
